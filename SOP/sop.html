2. Executive Summary & Project Understanding

2.1 What the client has asked for

From the client conversation, the requirement is a complete on-demand service platform consisting of:

  1. User Application — for end customers to browse services, book, pay and track.
  2. Vendor Application — for service providers/contractors to receive, accept, assign and complete jobs and get paid.
  3. Admin Panel — for the business to control users, vendors, pricing, bookings, money and content.
  4. Website — public marketing/landing site that drives customers and vendors into the apps.
  5. Live tracking across the booking journey, plus the “features as discussed”.
  6. A UI/UX matching the reference design shared by the client, delivered in 8–10 days.

2.2 Key finding from the analysis

We are not starting from zero. The repository already contains a working, feature-rich multi-role platform: a Node.js/Express + MongoDB backend with about 40 route modules and 45 data models, and a React 19 web application containing the public website, a mobile-style user/worker app shell, a vendor (contractor) panel, a corporate panel and a 40-page admin panel. Real-time (Socket.io), payments (Razorpay), push notifications (Firebase FCM), wallet, commission, referral, subscriptions, OTP-verified job start/end and a materials marketplace (“BuildMart”) are already implemented.

Therefore the 8–10 day plan is realistic only because the strategy is adapt & harden, not rebuild: re-skin the UI to the client’s reference design, align terminology and flows to the client’s business, complete and harden live tracking, close the gaps listed in Section 6, then test and deploy.

2.3 Delivery strategy in one view

PrincipleWhat it means in practice
Reuse firstEvery module that already works is kept; changes are configuration, copy and styling wherever possible.
Vertical slicesWork is organised by journey (Book → Track → Pay) not by file, so each day ends with something demonstrable.
Live tracking is the heroIt gets dedicated engineering time (Section 5) because it is the one feature the client named explicitly.
Freeze earlyScope is frozen on Day 1 sign-off; anything new goes through change control (Section 14).
Test continuouslyQA starts on Day 3, not Day 8; UAT on Day 8 is confirmation, not discovery.

2.4 Success criteria

  • A user can register, book, pay, watch the provider approach on a live map, complete the job and rate it — end to end, without manual intervention.
  • A vendor can be onboarded (KYC), approved, receive jobs, accept/assign, work, and withdraw earnings.
  • Admin can configure pricing/commission, approve vendors, monitor all bookings live and settle money.
  • The website is live, responsive and routes visitors to the correct app.
  • All Priority-1 test cases pass on the production environment before hand-over.

3.4 Core booking lifecycle (as implemented)

CREATED → BROADCASTING (nearby eligible providers receive NEW_BROADCAST) → ACCEPTED (first accept wins) → ASSIGNED → EN_ROUTE → STARTED (start OTP verified) → COMPLETED (end OTP verified)  |  exits: CANCELLED, FAILED (no provider within 10 minutes — auto, with wallet refund), REFUNDED.

Money is computed at booking time and stored on the booking: basePrice, platformFee, taxes, totalAmount, commissionAmount, laborShare, optional walletDiscount. Admin-configurable settings include platform fee (fixed/percent), B2B fee, global commission %, broadcast radius (10 km B2C, 50 km B2B), wallet/cash limits, cancellation penalty and time slots.

  • User/worker app shell (/app): ~30 pages — home, services, sub-category, checkout, tracking, bookings, wallet, refer & earn, KYC, earnings, notifications, BuildMart, address book, support.
  • Vendor panel (/vendor): dashboard, jobs, job detail, crew, attendance, earnings, analytics, mart products/enquiries/subscription, profile, support.
  • Admin panel: ~40 pages — dashboard, users, vendors, labour, bookings, categories/subcategories/services, zones, time slots, fees, commission, wallets & cash, banners, reviews, complaints, referrals, subscriptions, reports, CMS, settings.
  • Documentation present: frontend/docx (API contract, Postman collection, developer guide) and backend API notes (Vendor, Admin Booking, Job Allocations, BuildMart).

3.6 Housekeeping observations

  • The backend root holds many one-off scripts (check_*.js, fix_*.js, test*.js) — they are data-repair utilities and must not ship to production.
  • .env and a Firebase service-account JSON are present in the project — secrets must be rotated and kept out of version control and hand-over packages.
  • Several comments in routes/models show the product was built for a labour-hiring business; user-facing wording, seed data and icons must be re-aligned to the client’s business (Section 8).

5. Live Tracking — Current State, Gaps and Design

5.1 What already exists (verified in code)

PieceWhere
Worker device sends GPSActiveJob.jsx uses the browser watchPosition API while a job is active.
Socket relay to customersocket.js listens for LABOUR_LOCATION_UPDATE and forwards it to the customer’s private room.
Customer receives updatesJobTracking.jsx subscribes to LABOUR_LOCATION_UPDATE, BOOKING_ACCEPTED, BOOKING_STATUS_UPDATE.
Last-known location storageREST POST /labour/location/update and /status (provider location & online status; used for nearby matching).
Geospatial matchingBookings carry GeoJSON coordinates with a 2dsphere index; broadcast radius is admin-configurable.
Push fallbackFCM notifications for accept / status / failure.

5.2 Gaps to close

#GapWhy it matters / fix
1Location relay trusts customerId sent by the clientSecurity: any logged-in socket could push fake locations to any user. Fix: server looks up the booking, verifies the sender is the assigned provider, and derives the customer ID itself.
2No emission when the vendor (contractor) is the assigned partyAdd the same location sharing to the vendor job screen and to the assigned crew member where relevant.
3No stored route / breadcrumbPersist throttled points per booking so admin can replay and resolve disputes.
4No ETA / distance to destinationCompute from Google Directions/Distance Matrix (server-side, cached) and show “Arriving in X min”.
5Map visual on tracking page to be confirmed/completedShow provider marker, destination marker, route line, smooth marker animation.
6Reconnect & refresh behaviourOn reload, fetch last known point via REST, then resume socket stream. Persist active booking ID.
7Update frequency / batteryThrottle to one update every 5–10 s or 20 m movement; stop streaming when status is not EN_ROUTE/STARTED.
8Admin live view absentAdmin map of all active bookings with provider position and status.
9Background tracking limits of browser/PWAWeb geolocation pauses when the screen locks. Document clearly; mitigate with wake-lock and keep-screen-on prompt on the job screen.

5.3 Target design

Provider device — GPS every 5–10 s → socket: LOCATION_UPDATE {bookingId, lat, lng, heading, speed} → Server validates sender == assigned provider and booking status ∈ {EN_ROUTE, STARTED} → saves latest point + throttled breadcrumb → computes ETA (cached) → emits to customer room and admin live room → Customer map animates marker, updates ETA, shows status stepper.

Acceptance tests for live tracking

  • Provider moves 500 m → customer marker moves within 3 seconds.
  • Customer refreshes the page → marker reappears at last known position within 2 seconds.
  • A third user cannot receive, and cannot inject, another booking’s location.
  • Streaming stops automatically at COMPLETED / CANCELLED.
  • ETA shown is within ±20% of Google Maps for the same route.

7. Role-wise Workflows

7.1 User journey

  1. Open website / app → splash → choose to browse as guest or log in.
  2. Login with mobile number → OTP → profile created.
  3. Choose service → category → sub-category → service.
  4. Set address & time → map pin / autocomplete → Instant or Scheduled slot.
  5. Review bill → base price + platform fee + tax = total; optional wallet credit.
  6. Pay → Online (Razorpay) or Cash.
  7. Searching → broadcast to nearby providers; user sees “Finding your provider”.
  8. Accepted → provider name, photo, phone, rating shown; live map starts when EN_ROUTE.
  9. Arrival & start → user shares start OTP; status STARTED.
  10. Completion → end OTP; payment settles; rating & review prompt; receipt.
  11. After → booking history, rebook, complaint, referral.

User edge cases

  • No provider accepts in 10 minutes → booking FAILED, wallet discount refunded, user notified.
  • User cancels before accept → free; after accept → policy/penalty as configured.
  • Payment failed → booking stays unpaid; retry or switch to cash.

7.2 Vendor journey

  1. Register → business details → upload KYC documents → submit for verification.
  2. Wait for approval → admin approves or rejects with reason; vendor notified.
  3. Go online → toggle availability; location shared for matching.
  4. Receive job → popup with service, distance, earning, countdown → Accept / Reject.
  5. Assign crew (if applicable) → select member; replace if unavailable.
  6. Navigate → Start journey (EN_ROUTE), live location shared, “Open in Google Maps”.
  7. Start work → enter customer start OTP + start photo.
  8. Finish work → end OTP + end photo; collect cash if cash booking.
  9. Earnings → wallet credit minus commission; withdraw to bank; admin approves.

Vendor edge cases

  • Cash dues above limit → vendor blocked from new jobs until cleared online.
  • Cancel after accept → penalty debited from wallet.
  • Offline mid-job → last location retained; customer sees “location last updated X min ago”.

7.3 Admin journey

  1. Login → dashboard KPIs (bookings, revenue, active vendors, pending approvals).
  2. Approve vendors → review documents → approve/reject.
  3. Configure → categories, services, prices, zones, slots, fee, commission, radius, limits.
  4. Monitor → all bookings, live map, intervene (reassign/cancel/refund) via admin booking API.
  5. Finance → wallets, cash collected, withdrawals approve/reject, commission report.
  6. Content & support → banners, FAQ, legal; complaints; reviews.
  7. Reports → export for accounting.

7.4 End-to-end sequence

User books → System broadcasts → Vendor accepts → User + Admin notified → Vendor EN_ROUTE (live map) → Start OTP → Work → End OTP → Payment settled (commission split) → Ratings → Wallet / withdrawal → Admin reports.

The client wants the UI/UX “like this” (reference design shared in the conversation). The existing app already has a design system (components/app-ui: buttons, cards, inputs, navigation, feedback, typography; Tailwind 4 theme tokens in src/themes). 8.2 Design rules

  • One primary action per screen; sticky bottom CTA on mobile.
  • Booking status always visible as a stepper; colours: pending (amber), active (blue), done (green), failed/cancelled (red).
  • Skeleton loaders for lists, empty-state illustration with action for every list.
  • Accessible contrast (WCAG AA), minimum 14 px body text on mobile.
  • Maps: full-bleed with bottom sheet containing provider card, ETA, call/chat, OTP.
  • Motion: subtle (Framer Motion), never block the user; respect reduced-motion.

12.4 Go-live runbook

  1. Code freeze on the release branch; tag v1.0.0.
  2. Take database snapshot (if migrating data) and record current DNS values.
  3. Deploy API → run health check → run seed (categories, settings, admin) once.
  4. Deploy web apps with production environment variables (VITE_API_URL, Maps, Razorpay key ID).
  5. Switch DNS; verify SSL; verify WebSocket connects on the production domain.
  6. Smoke test T01–T05 and T15 on production with a real ₹1–10 transaction and refund.
  7. Announce to client; start hyper-care.

12.5 Rollback

  • Trigger: any S1 in the first 2 hours, or payment/tracking failure rate > 5%.
  • Action: redeploy previous tag (static apps are instant on Vercel; API via PM2 / previous image), restore DB snapshot only if data corruption is confirmed.
  • Owner: DevOps executes, Project Lead decides, client informed immediately.

12.6 Hyper-care (first 7 days after go-live)

  • Daily review of error logs, failed payments, stuck bookings (cron already auto-fails broadcasts after 10 min).
  • Same-day response for S1/S2 issues; daily 5-line health report to client.
  • Hand-over: admin user guide, vendor onboarding guide, API docs, credentials register (delivered securely), and one live training session.

13. Risks, Assumptions, Dependencies & Out-of-Scope

13.1 Assumptions

  • The delivered system is built on the existing codebase; it is not a rewrite.
  • “Application” means a responsive web app installable as a PWA. Native Android/iOS store apps are separate work.
  • The reference UI is of mobile-app scale (about 15–25 screens). A much larger design needs re-estimation.
  • The client supplies all third-party accounts and keys in Day 1–2.
  • One city/zone and one language (English) at launch; Hindi/other languages are additive.
  • The business domain of the client matches the “book a provider → track → pay” model of the existing platform. If the client’s domain differs materially (e.g. car-specific inventory, listings, community feed), those parts are additional scope.

14. Change Control, Acceptance & Sign-off

14.1 Change-control procedure

  1. Raise: any new or changed requirement is written in the change log (what, why, who asked).
  2. Assess: Project Lead estimates effort, timeline and risk impact within 4 working hours.
  3. Decide: client chooses one — (a) accept with extra days, (b) swap with an equal-sized item, (c) move to Phase 2.
  4. Record: approved changes update this SOP version and the day plan.
Rule: after Day 1 freeze, a request that adds more than 0.5 day of work is never absorbed silently — it is either swapped or moves the date.

14.2 Definition of Done (per feature)

  • Implemented and merged to staging; no console or server errors.
  • Works on mobile viewport and one real phone.
  • Role/permission checks in place; inputs validated.
  • Test scenario(s) pass; demo shown to Project Lead.
  • Wording and visuals match the approved design.
